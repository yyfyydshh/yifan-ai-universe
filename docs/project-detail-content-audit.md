# 项目详情内容审计与重构基线

状态：内容与结构待确认；尚未进入参考图重构或页面实现。

## 1. 本轮目标

让招聘方在 30 秒内回答四个问题：

1. 这个项目解决什么业务问题？
2. 杨逸凡具体设计或交付了什么？
3. Agent 如何处理输入，并在哪些位置控制错误？
4. 有哪些真实仓库、输出格式或验收规则可以复核？

当前详情页的主要问题不是视觉精度，而是表达重复。右侧正文、左侧观测图和移动端场景重复呈现同一份摘要；抽象的点、线、漏斗和打勾矩阵没有编码新的项目事实，因此增加了视觉负担，却没有提升理解速度。

## 2. 推荐页面结构：项目证据档案

### A. 30 秒摘要

- 项目定位：一句话说明服务对象与业务结果。
- 典型输入：用户实际提供什么。
- 核心输出：最终能拿到什么。
- 我的角色：需求拆解、工作流设计、实现、测试、文档或运营中的真实职责。
- 状态标记：真实项目、脱敏概要、可运行 Skill、方法 SOP 或演示项目。

### B. 一张真实工作流

只保留一张语义流程图：

`输入 → 处理与判断 → 质量门 → 交付物`

每个节点必须对应仓库或用户材料中的真实步骤。不同项目可以有不同节点数量，但不再为六个章节各画一张抽象图。

### C. 关键设计判断

保留 2–3 个真正体现个人判断的决策，每个决策采用固定格式：

- 为什么这样设计；
- 避免了什么风险；
- 如何在流程或输出中落地。

### D. 可靠性与边界

不用抽象打勾矩阵，改为三组可读信息：

- 会验证什么；
- 什么情况下停止、降级或留空；
- 明确不承诺或不执行什么。

### E. 交付物与验证

- 真实输出格式；
- 可公开仓库或脱敏说明；
- 运行前提；
- 可执行的检查命令、门槛或验收规则；
- 视频演示预留位。

### F. 复用价值

只保留一句可被证明的迁移方向，不再单独制作抽象扩散图。

## 3. 七个项目的事实映射

### 01 全球舆情与品牌口碑分析 Skill

来源：`yyfyydshh/global-public-opinion-analysis-skill`

- 项目定位：面向产品 VOC、品牌口碑与商业事件的全球公开网页舆情分析工作流。
- 典型输入：分析主题、时间范围、目标有效数据量、市场/语言、竞品和关注维度。
- 工作流：只读连接器检查 → 主题范围门禁 → 来源策略与运行清单 → 分批采集 → 去重、质量筛选与来源审计 → 报告门槛 → 多格式交付。
- 关键门槛：正式报告至少需要 100 条有效记录、5 个来源域名、2 种来源类型，并通过来源策略审计；未达到时只交付数据包、覆盖缺口和续采建议。
- 真实输出：候选预览、六工作表 Excel 数据包、Markdown 正式报告，以及用户明确需要时生成的离线 HTML。
- 边界：不适用于政治、战争、军事、武器或情报主题；不把不足样本包装成正式结论。
- 当前站内误差：输出缺少 Excel 与 Markdown；可靠性描述过于笼统，没有展示正式报告的可量化门槛。

### 02 销售协作助手

来源：`yyfyydshh/sales-copilot-overview`；仓库为脱敏高层概要。

- 项目定位：把客户聊天、拜访记录或线索备注整理为可复核、可执行的下一步建议。
- 典型输入：客户聊天、销售记录、拜访纪要或线索备注。
- 工作流：场景检查 → 事实/假设/未知分层 → 线索画像 → 机会优先级 → 单一解决方向 → 已核验材料建议 → 下一句跟进话术与内部动作。
- 关键门槛：信息不足时不补分、不猜测；没有可靠材料时保持为空；所有外发内容只生成草稿，由销售人工决定。
- 真实输出：客户判断、建议动作、需追问的关键问题、聚焦方案方向、可核验材料建议和回复草稿。
- 边界：不执行自动化、采集、部署、消息发送或报价。
- 证据分层：MQL A—D、严格 JSON 契约、白名单链接和子 Skill 编排来自用户简历与项目陈述；公开概要仓库刻意不披露评分细则、内部 Skill、案例、链接或业务数据。页面必须明确区分“脱敏公开概要”和“用户提供的项目事实”。
- 当前站内误差：把内部能力直接写成公开仓库可验证事实，缺少“脱敏概要”的状态说明。

### 03 Mintlify 文档站搭建、迁移与维护 SOP

来源：`yyfyydshh/mintlify-docs-site-sop`；八爪鱼文档站真实项目经历来自用户简历。

- 项目定位：把产品目标、帮助中心、文章清单或本地 HTML 转化为可维护、可预览、可发布、可持续更新的 Mintlify 文档站。
- 三条路径：从零搭建、旧站迁移、日常维护。
- 工作流：业务输入 → 事实核验 → 信息架构 → 内容与媒体迁移 → 导航、链接与重定向 → 本地验证 → 托管验收 → 受控发布 → 持续维护。
- 关键门槛：结构先行；动态产品能力需要真实证据；正文、媒体、链接、锚点和移动端一起迁移；本地预览不等于托管验收；远程写操作和正式发布需要明确授权。
- 真实输出：信息架构、MDX 页面、媒体本地化、路由映射、迁移记录、检查清单、发布确认单、故障决策树和维护流程。
- 证据分层：仓库证明可复用 SOP；用户简历证明其独立推进八爪鱼产品文档站 0→1、内容迁移、导航搜索、审核发布与持续维护。页面不能把 SOP 仓库冒充为完整生产站源码。
- 当前站内误差：项目名只强调“八爪鱼 0→1”，但 GitHub 指向的是通用 SOP；需要同时说明真实项目经历与公开方法沉淀的关系。

### 04 金融监管动态风险监测 Skill

来源：`yyfyydshh/financial-regulatory-risk-monitor`

- 项目定位：把中国金融监管通知、法规和处罚数据与企业画像逐项匹配，生成带证据门槛的企业风险报告。
- 典型输入：已确认的最新采集任务、完整导出、企业画像、投递渠道与固定目标。
- 工作流：输入校验 → 当前任务启动与全量导出 → 规范化、去重与快照留痕 → 语义审阅与证据覆盖校验 → 适用性判断与风险分级 → HTML 报告 → 预检后投递或人工查看。
- 关键门槛：当前批次隔离、完整数据而非预览样本、证据索引、地域/主体/业务活动/时间条件匹配、低置信度降级、重复投递拦截。
- 真实输出：独立 HTML 风险报告、证据索引、语义审阅台账、分析清单和可选投递回执。
- 边界：处罚记录代表执法关注，不等于目标企业已经违法；报告是合规决策支持，不构成法律意见。
- 当前站内误差：缺少全量导出、企业画像、适用性判断和“处罚不等于企业违法”这一核心边界。

### 05 招投标公告语义清洗 Skill

来源：`yyfyydshh/tender-cleaner-semantic-29field-skill`

- 项目定位：把跨来源招标、采购、中标、成交或废标公告统一为固定 29 字段 CSV/JSON。
- 两类输入：本地 JSON、CSV、TSV、XLSX、XLSM、XLS；或八爪鱼账户中已经存在的任务。
- 工作流：输入解析/任务精确匹配 → 全量导出 → 正文语义提取 → 29 字段契约 → 金额规范化 → 去重 → 逐条异常隔离 → CSV/JSON。
- 关键门槛：没有原文依据的字段留空；预览 sampleData 不作为全量数据；只把预算、最高限价或控制价识别为招标金额；API Key 不写入文件或 Git。
- 真实输出：固定 29 列 UTF-8-BOM CSV、固定 29 字段 UTF-8 JSON、异常与处理统计。
- 当前站内误差：方向基本正确，但没有让读者看到“双路径输入”和“固定 29 字段”到底意味着什么。

### 06 文学文风自适应 Humanizer 套件

来源：`yyfyydshh/humanizer-literary-suite`

- 项目定位：仅面向小说、散文、叙事文学和文学化非虚构，在保护作者声音与叙事完整性的前提下做最小幅度去 AI 味编辑。
- 两种模式：至少三篇作者代表作的恒稳模式；单篇目标稿的临时画像模式。
- 工作流：识别文学文本与模式 → 文风画像 → 用户确认 → 内容锁定 → 最小幅度编辑 → 确定性与语义完整性审计 → 四角度独立复核 → 最多三轮安全返修 → 另存交付。
- 系统结构：主编排、文风画像、文学编辑、完整性审计、四角度复核五个模块。
- 关键门槛：画像确认前不改稿；不得改变剧情、人物、视角、时间线、关键对白、意象、情绪曲线或结局；不覆盖原稿；风险分只是启发式风险，不是 AI 比例或来源鉴定。
- 真实输出：文风画像、内容锁定清单、另存修改稿、完整性结果和独立审阅报告。
- 当前站内误差：现有描述过短，把一个五模块套件弱化成“实验项目”；建议提升为完整的专业创作工作流，但不能把它描述为通用文案工具。

### 07 热点快报 Skill

来源：`yyfyydshh/hot-news-brief-skill`

- 项目定位：从公开商业新闻中筛选最近 7 天的有效报道，生成短小、可点击、证据关联的简报。
- 典型输入：公司、行业、产品、技术或商业事件主题，以及 news_list、decision_brief、content_radar 或 both 输出模式。
- 工作流：主题与输出确认 → 只读连接器检查 → 严格 7 天检索 → 标题/URL/日期校验 → 去重、来源均衡与排序 → 新闻清单、决策简报或选题雷达。
- 关键门槛：只保留标题、HTTP(S) URL 和有效发布日期齐全的记录；排除未来日期和时间窗外内容；不编造链接、引文、热度或因果关系；没有合格新闻时明确返回空结果。
- 真实输出：0–3 条短摘要、最多 10 条可点击新闻，以及有证据支撑的决策影响或内容角度。
- 边界：不处理政治选举、军事冲突、主权争议、武器部署或情报主题；结果代表本次检索覆盖，不代表完整新闻全貌。
- 当前站内误差：站内写成“定时触发、定时快报”，但仓库没有定时调度能力；应删除该主张，改为“严格七天窗口的只读检索与证据简报”。

## 4. 全站层面的优化建议

### 高优先级

1. 用“项目证据档案”替换六章能力观测台；删除重复的桌面/移动场景图。
2. 扩展 `Project` 数据模型：`audience`、`inputs`、`role`、`workflow`、`gates`、`deliverables`、`prerequisites`、`boundaries`、`evidenceStatus`。
3. 所有项目首屏明确证据状态：可运行仓库、脱敏概要、方法 SOP、真实经历佐证或演示项目。
4. 一张工作流图只编码真实节点；没有真实关系的线、点、轨道和漏斗全部删除。
5. 修正热点快报的“定时”表述，并补足舆情、监管、文档站和 Humanizer 的关键事实。

### 中优先级

1. 视频占位从大面积空框缩为“演示待共创”入口；有视频后再提升视觉权重。
2. 将 GitHub 入口改为更准确的动作词：查看 Skill、查看脱敏概要、查看 SOP，而不是统一写“查看代码”。
3. 工作流节点支持点击或键盘聚焦后查看“输入/动作/校验/输出”，但默认视图保持短而清晰。
4. 在项目之间采用同一阅读骨架，不强迫同一视觉图形；数据项目可用字段样例，分析项目可用证据链，写作项目可用审计回路。

### 低优先级

1. 在有真实脱敏样例后加入一张输入/输出对照。
2. 后续短视频只演示一次完整任务，不重复页面已经写清的项目介绍。

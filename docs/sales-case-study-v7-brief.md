# 销售专业助手项目页 v7 内容与交互 brief

状态：`reference-invalidated`。v6 的视觉完成度可以保留，但主表达仍然以“机制、检查、状态”为中心，招聘方必须先理解术语，才能知道项目有什么用。

## 访客与三秒目标

- 主要访客：招聘方、AI 应用岗位负责人、产品与销售运营负责人。
- 三秒目标：知道这是一个读取客户沟通、帮助销售判断下一步的 AI 销售专业助手。
- 十秒目标：看见一个具体例子——客户说了什么，助手给销售什么答案。
- 三十秒目标：理解答案为何可复核：只引用原话、把未知项单独列出、信息不足先追问、外发由销售确认。

## 已确认事实与来源

- 公开仓库：`https://github.com/yyfyydshh/sales-copilot-overview`。
- 仓库确认的输入：客户聊天、拜访记录、会议纪要或线索备注。
- 仓库确认的能力：梳理客户事实与未知项、判断机会优先级、形成聚焦解决方向、在授权资料范围内匹配材料、生成下一句跟进话术和内部动作。
- 仓库确认的边界：不自动登录、采集、部署、报价或发送消息；所有外发内容都是草稿。
- MQL A—D、严格 JSON 契约和子 Skill 编排属于用户明确提供的内部项目事实，只放在第二层“专业能力与实现”中，不承担首屏解释任务。

## 一句话定义

销售把客户聊天交给它，它帮助销售看懂客户、找出还缺什么信息，并明确下一步该问什么、该做什么。

## 首屏主张

### 标题

`把客户的一段话，变成销售下一步该做的事。`

### 说明

`输入客户聊天、会议纪要或销售记录；输出客户问题、待确认信息、下一步行动和一条可编辑的追问。`

### 角色边界

`它是销售的判断助手，不替销售自动发消息、报价或实施。`

## 主交互：客户原话 → 助手答案

主界面只保留两个明确对象，不再使用三栏“输入 / 可靠性检查 / 输出”工作台。

### 左侧：客户原话

- 标题直接写“客户原话”，不使用“原始沟通”“输入端”等抽象词。
- 使用 3 句明确标注的脱敏机制示例，不冒充真实客户记录。
- 当前答案所引用的原话片段会被细线和低饱和紫色标出。
- 没被引用的句子保持安静，避免整栏同时发光。

机制示例草案：

1. 客户：`我们现在的线索比较分散，经常跟进不及时。`
2. 客户：`团队里的案例和资料也不好复用。`
3. 销售：`目前团队怎么记录、分配和跟进线索？`

### 右侧：销售专业助手给出的答案

默认完整显示四个普通人可以直接理解的结果，不要求点击后才知道项目价值：

1. `客户当前的问题`：线索分散、跟进不及时、团队资料难复用。
2. `还需要确认`：当前使用什么工具；团队如何记录、分配和复盘线索。
3. `建议下一步`：先确认现有流程与协作方式，再安排针对性方案讨论或演示。
4. `建议这样问`：方便介绍一下团队目前如何记录、分配和跟进线索吗？

点击任一结果时：

- 左侧只高亮支持该答案的原话。
- 结果下方出现一句“为什么这样判断”，使用普通语言解释依据。
- 不打开独立侧栏，不重复同一组要点。

### 信息不足情境

保留一个次要情境切换：`已有足够信息 / 还缺关键信息`。

- 足够信息：展示四项答案。
- 信息不足：只保留“还需要确认”和“建议这样问”；客户画像、优先级和方案方向显示为“暂不判断”，不是报错，也不是假运行状态。

## 第二层：它为什么可靠

主示例下方使用一条短证据带，不与结果争夺第一焦点：

- `只引用客户原话`：关键判断可以回到输入内容。
- `推测单独标记`：事实、合理假设和未知项不混在一起。
- `信息不足先追问`：不补分、不猜测客户情况。
- `外发由销售确认`：话术和建议保持为可编辑草稿。

再往下才进入“专业能力与实现”：MQL A—D、严格 JSON 契约、主/子 Skill 编排、白名单资料。这里回答“它如何被做得稳定”，而不是“它是什么”。

## 交互与动效边界

- 原语一：结果聚焦——选择结果时只改变对应结果和原话证据的 `opacity` / `transform`。
- 原语二：证据连线——一条短路径从结果指回来源，但不得穿过文字。
- 原语三：情境切换——足够/不足状态使用不超过 150ms 的交叉淡入。
- 不使用运行计时、成功动画、模拟 Agent 输入中、流程节点巡航或假 KPI。
- reduced-motion 下取消空间位移，只保留即时状态与可读的边框/颜色差异。

## Render contract

- `THREE_SECOND_MESSAGE`：把客户的一段话，变成销售下一步该做的事。
- `PERSONAL_EVIDENCE`：公开仓库确认的事实/假设/未知分层、机会优先级、聚焦方案、授权资料和人工外发边界；内部事实在第二层明确标注来源状态。
- `AUTHORED_MOVE`：选择右侧一个普通语言答案，左侧只点亮支持它的客户原话，让“答案从哪里来”成为交互本身。
- `PRIMARY_FOCAL_POINT`：客户原话与销售专业助手答案的直接前后对照。
- `SECONDARY_ANCHORS`：信息不足情境；四条可靠性边界。
- `READING_PATH`：一句话定义 → 客户原话 → 助手答案 → 为什么可靠。
- `WHITESPACE_MAP`：两栏之间只保留证据路径所需的窄通道；底部留白用于进入可靠性第二层，不使用固定高度填充。
- `SEMANTIC_GRAPHIC`：唯一连线表示“当前答案引用了哪一句客户原话”。
- `OVERLAP_LEDGER`：none。
- `EXCLUSION_ZONES`：客户原话、四项答案、机制演示声明和人工确认边界必须完整可见；连线不能进入文字框。
- `VIEWPORT_PAYLOAD`：桌面首屏完整看见定义、至少两句客户原话和四项答案；移动端先显示定义与客户原话，随后紧邻显示四项答案，不插入机制面板。
- `Archetype`：`C0 code-only`。
- `Topology`：`section-specific`，只属于 Sales Copilot。

## 禁止项

- 首屏出现 MQL、JSON、白名单、子 Skill 等实现术语。
- 三栏仪表盘、可靠性检查作为中间关卡、同权重七项结果墙。
- 重复解释同一条要点的右侧深度面板。
- 把脱敏机制示例描述成真实客户案例。
- 把建议话术描述成已经发送或自动执行的结果。
